# Health City Pharmacy - Financial Information System

React and Express implementation of the Health City Pharmacy FIS prototype. MongoDB Atlas is the required runtime database; legacy JSON records are retained in `backend/data/` as migration sources and are not an active fallback.

## Windows 11 setup

Open PowerShell in this project directory:

```powershell
cd "C:\Users\DELL\Downloads\FIS GROUP ASSIGNMENT\FIS_Assignment_Output\FIS_Prototype"
npm run install:all
npm run dev
```

Open http://localhost:5173.

The backend API is at http://localhost:4000/api.

The existing password hashes are preserved and stored in MongoDB; plaintext passwords are never migrated or returned by the API. No employee identity or password is generated by setup.

New users can select **Create a new account** on the login screen. Registrations are assigned the Cashier role, stored with a password hash, and require System Administrator approval before sign-in. Users cannot choose their own role.

## Deployment (Vercel + Render)

The frontend is deployed from `frontend/` on Vercel; the API is deployed from `backend/` on Render. The root `render.yaml` is a Render Blueprint for the API on Render's free compute plan, and `frontend/vercel.json` configures client-side route fallback. Free Render services spin down after 15 minutes without traffic, so the first request after inactivity can take about a minute; this plan is intended for prototypes, not production.

1. Create a MongoDB Atlas database and database user. Allow connections from the Render service's outbound IP addresses in Atlas Network Access.
2. In Render, create a Blueprint from this repository and use `render.yaml`. Set `MONGODB_URI` to the Atlas connection string and keep the generated `JWT_SECRET` private. `MONGODB_DATABASE` is preconfigured by the Blueprint.
3. In Vercel, import the repository and set the project Root Directory to `frontend`. Add `VITE_API_BASE_URL` as `https://<your-render-service>.onrender.com/api`, then deploy.
4. Set the Render `CORS_ORIGIN` environment variable to the exact Vercel site origin, such as `https://<your-project>.vercel.app` (no path or trailing slash). Include additional comma-separated origins only when needed, then redeploy the Render service.
5. To migrate the existing local JSON records, configure `backend/.env` locally with the target Atlas connection and run `npm run migrate:json --prefix backend`. Review the migration output before using the deployed app.

Never commit `.env` files, MongoDB credentials, JWT secrets, or `backend/data/` JSON files. That folder contains local customer and employee records and is intentionally excluded from Git; perform any required migration locally rather than uploading those records to GitHub. Do not use the development database or demo user accounts for real business data.

## Storage

MongoDB Atlas is required. The server verifies the database connection and indexes before listening; startup fails if Atlas cannot be reached. The backend never falls back to JSON. A local `backend/data/` snapshot can be used as a migration source, but it is intentionally excluded from Git because it may contain customer and employee records. Backups remain in `backend/backups/`; neither data nor backups are served to the React app.

When a trusted local migration snapshot is present, check it without connecting to Atlas using `npm run migrate:json --prefix backend -- --dry-run`, then import it with `npm run migrate:json --prefix backend`. The script is rerunnable, does not overwrite conflicting MongoDB records, checks references and reports counts and failures. It does not import or modify backup snapshots. All original JSON files remain unchanged.

Financial values are stored as integer minor units. Illustrative monthly summaries are excluded from active settings, and incomplete historical sales are labelled and excluded from complete financial totals. Missing sale amounts are not estimated from current product prices.

POS sale, payment, stock, and audit writes use MongoDB transactions.

## Customer registration and point of sale

Customers are stored separately from employee accounts in the `customers` collection. Authorized employees can register and update customer profiles from the Customers module. Customers never receive employee roles or staff permissions. The Transactions module supports registered customers and walk-in sales; completed sales update stock, payment, stock-movement and audit records. Customer purchase history is derived from completed sales and refund records.

Customers can also register and sign in through **Customer sign in or register** on the employee login screen, or directly at `/customer-portal`. Customer accounts activate immediately and use a separate MongoDB collection for credentials and customer-only API access. Customers can view in-stock products, place an order, choose M-Pesa, EcoCash, E-wallet, or Credit Card, and see the completed purchase in their history. Checkout uses the same atomic MongoDB sale, payment, stock, stock-movement, and audit writes as the cashier POS, so customer orders appear in cashier transaction history with products and the recorded payment method. This prototype records the selected method as paid but has no external payment gateway and does not charge a real account. Connect and verify a payment provider before using online checkout for real-money sales.

## Security notes

Customer and employee passwords are bcrypt-hashed, and their JWT tokens use separate role checks and an eight-hour expiry. Customer registration and login are rate limited. Customer portal tokens are stored in browser local storage for this prototype; there is no verified phone/email OTP or password reset. Use a private development JWT secret and do not deploy this assignment as a production system.
